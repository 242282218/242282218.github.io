# 站点 ↔ 写作软件契约

写作软件（`apps/writer/`）与站点在同一个仓库里，但它们是**两个独立安装的项目**：
各自有 `node_modules`、各自的技术栈与脚本，`pnpm-workspace.yaml` 并不存在。
软件在运行时也不直接依赖这个仓库——首次连接会在应用数据目录里建自己的 clone。

两者之间靠本文这份契约耦合。契约里的任一项漂移，都要等到用户点「发布」走到构建
闸门才会暴露，或者更糟——静默写坏站点。因此站点侧的 `tests/writer-contract.test.ts`
把下述每一项都从**两侧的源文件里解析出来**做比对，漂移会在 `pnpm test` 阶段失败。

改契约里的任何一项时，请同时更新本文件与那个测试。

## 1. 受管目录

| 用途 | 写作软件（权威定义） | 站点侧对应物 |
|---|---|---|
| 文章正文 | `paths.rs` 的 `BLOG_DIR_PREFIX` = `src/content/blog/` | `src/content.config.ts` 的 `loader: glob({ base: './src/content/blog' })` |
| 文章配图 | `paths.rs` 的 `IMAGE_DIR_PREFIX` = `public/blog/` | `public/` 静态目录（构建时原样输出） |
| 构建产物 | `.cargo/config.toml` 的 `target-dir` = `../.build/writer-target`（**不在仓库内**） | — |

软件只允许改动这两处受管路径之下的文件，并在写入前逐段复核路径上没有符号链接／
目录联接逃逸。文章目录两侧必须一致，否则软件「保存成功」但站点读不到。

## 2. front matter 字段

软件会改写的受控字段由 `article_io.rs` 的 `KNOWN_FIELDS` 定义，当前为：

```
title  description  pubDate  updatedDate  tags  draft
```

这些字段必须全部在站点 `src/content.config.ts` 的 schema 中声明。软件按行做字节级
手术：**值未变化的字段整行保持原样**（含注释与引号形式），未知字段与字段顺序原样
保留，因此站点的 schema 是唯一的字段权威，软件不去「修复为默认值」。

## 3. 发布闸门

软件发布前会在隔离副本中依次运行 `pnpm test` / `pnpm check` / `pnpm build`
（`preview.rs` 的 `run_site_checks`），任一失败即**停止发布**。因此站点
`package.json` 必须始终提供这三个脚本。这三个脚本的语义也是契约的一部分：
`test` 应当断言站点自身不变量，`check` 做类型检查，`build` 产出可部署产物。

## 4. 分支

| 分支 | 定义位置 | 含义 |
|---|---|---|
| `writing` | `sync.rs` 的 `WRITING_BRANCH` | 远程保存的草稿 |
| `main` | `sync.rs` 的 `MAIN_BRANCH` | 网站当前版本 |

`.github/workflows/deploy.yml` 必须监听 `main`（否则发布不生效），且**不得**监听
`writing`（否则未发布的远程草稿会直接上线，违反软件向用户承诺的公开性说明）。

## 5. 两处安装边界

- 站点命令：`pnpm test` / `pnpm check` / `pnpm build`（仓库根）。
- 软件命令：`pnpm --dir apps/writer test` / `typecheck` / `build`，以及
  `smoke` / `crash-recovery`。
- 两者不可混用；软件有自己的 `pnpm-lock.yaml` 与 `node_modules`。
- 根 `tsconfig.json` 必须 `exclude: ["apps"]`，否则 `astro check` 会扫描软件的 Vue
  文件并报 `@astrojs/vue` 缺失。

## 6. 软件的验收脚本

软件的验收脚本放在 `apps/writer/scripts/`（它自己的包内），不放在站点根的
`scripts/`：它们只依赖软件自己的产物，按包内路径解析可执行文件。

| 命令 | 作用 |
|---|---|
| `pnpm --dir apps/writer smoke` | 安装包冒烟：全新数据目录启动 + `--self-test` 完整通路 |
| `pnpm --dir apps/writer crash-recovery` | 真实强杀进程后的崩溃恢复验收 |

可执行文件的位置由 `scripts/lib/writer-exe.mjs` 向 `cargo metadata` 询问
`target_directory` 得到，因此**不写死路径**——`target-dir` 移到仓库外后仍然可用。

站点侧与之相关的检查是 `scripts/test/check-site-drafts.mjs`：它用真实构建验证
`draft: true` 的过滤与 `public/blog/<article-id>/` 图片的输出，属于跨界的守约检查，
因此留在站点根。
